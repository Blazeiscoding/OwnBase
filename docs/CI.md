# CI duration and caching

Checks keep all seven workspace typechecks, all five unit-test tasks, three builds, both bundle-size guards, the browser E2E suite and the visual check. Desktop and Container run when their artifact inputs change, including shared UI and client-core code. Ordinary Markdown changes skip these workflows; `docs/INTEGRATIONS.md` runs Checks because the integration contract tests read it.

Checks runs as eight Linux jobs side by side, so a run lasts about as long as its longest job instead of all of them in a row (about ten to twelve minutes in one job before):

| Job                                              | What it runs                                                                                                                                                                                 |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `checks`                                         | Formatting, the automation typecheck, the cache-input and script tests, every typecheck, protocol/client-core/desktop unit tests, the three builds and their guards, and the artifact lookup |
| `unit (server)`                                  | The server's unit tests                                                                                                                                                                      |
| `unit (ui 1 of 2)`, `unit (ui 2 of 2)`           | ui's unit tests in two halves (`vitest --shard`)                                                                                                                                             |
| `browser (e2e 1 of 3)` to `browser (e2e 3 of 3)` | The browser suite in three parts (`playwright test --shard`)                                                                                                                                 |
| `browser (visual)`                               | The visual check                                                                                                                                                                             |

Every job installs on its own, about half a minute; the repository is public, so the standard runners' minutes cost nothing. The browser jobs build only the server CLI and the web client it serves (`turbo run build --filter=ownbase-server`), from the task cache when an earlier run's `checks` job built the same source.

Measured on #354 (2026-10-24): Checks took 3 minutes 29 seconds from start to finish on a cold task cache, and 3 minutes 36 seconds on the next push, where `checks` and the unit jobs replayed from the cache in 16–40 seconds. Before, the one job took 10–12 minutes. The longest job is the first e2e part (3 minutes 26–34 seconds, 168 seconds of it tests), because the call and WebRTC scenarios come first in the file and shards are contiguous; the other parts take about two minutes. Desktop took 3 minutes 29 seconds with the installer, against about four minutes before.

The browser suite is one file, and Playwright splits shards by file unless `fullyParallel` is on. It is on in `playwright.config.ts`: every scenario starts a workspace of its own (REV-08), so order does not matter, and with one worker a local run is unchanged. Shards split by count, fifteen scenarios each.

Linux uses Turbo for the final builds as well as typechecks and tests. The server CLI depends on the web client, so earlier phases already build that client. `pnpm build --concurrency=2` reuses it rather than rebuilding it with a separate package command. Task concurrency is limited to two and each Vitest task gets at most two workers through `VITEST_MAX_THREADS` and `VITEST_MAX_FORKS`; this avoids starting every package's worker pool simultaneously. These variables are declared and hashed only for test tasks. The cache-input check proves that changing worker limits invalidates tests while preserving build/typecheck hashes. Passing Vitest flags through Turbo forwards them to dependency builds too, so the unit job runs one test task alone with `--only` (`turbo run test --filter=@ownbase/ui --only -- --shard=1/2`): its dependencies have no builds, so nothing is skipped, the flag reaches Vitest alone, and each half is cached under its own hash. Formatting, cache-input verification, bundle guards and browser tests still run on every applicable workflow.

The task-cache archive contains only `.turbo/cache`. Its key includes runner OS and architecture, the actual Node version, the lockfile, Turbo configuration, the job (`checks`, `unit-server`, `unit-ui-1`, `unit-ui-2`) and commit. A job starts from its own latest archive; `checks` falls back to any job's, and the browser jobs restore `checks` archives without saving their own. Compatible earlier archives supply content-addressed entries; Turbo decides whether each task's source, configuration, dependencies and environment still match. Entries expire after seven days and the local cache is capped at 100 MB. Root TypeScript/install configuration and test inputs outside a package are declared explicitly, such as the page scripts ui's tests read (`first-paint.js` in both apps and `notification-worker.js`). Package-specific test tasks retain their workspace dependency hashes, including packages that export source without a build script. `node scripts/check-ci-cache.mjs` tests eighteen source/configuration changes and 112 invalidation or preservation assertions in an isolated temporary workspace, and verifies that the web-build hash is the same across all three phases.

[GitHub cache scope](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache) allows later runs of the same PR to restore its cache and PRs to restore default-branch caches. One PR cannot supply another PR's task cache or overwrite a default-branch cache. The existing dependency-cache workflow on main fills pnpm and Chromium caches; it does not prime Turbo results or Electron downloads. A new PR can therefore still start cold. Jobs running project code use `pull_request` with read-only repository permissions. Artifact deletion runs in a separate job. Cache archives contain task outputs and logs and must not be treated as a security boundary.

Ordinary runtime PRs package Windows with `--win --dir`. This produces `win-unpacked/OwnBase.exe`, which is what desktop E2E launches, while avoiding an unused NSIS installer. PRs changing installer configuration, resources, package manifests, lockfile, install configuration or the selection policy still build the installer. If the base diff cannot be read, selection defaults to full installer coverage. Manual Desktop runs also default to the installer, with an input to choose an unpacked build. Electron and electron-builder downloads use an OS/architecture cache; their self-versioned cache directories allow reuse across lockfile changes within permitted GitHub cache scopes.

The packaged app's nine scenarios took 163–169 seconds of a four-minute Windows job, so Desktop runs two jobs side by side, `windows (1 of 2)` and `windows (2 of 2)`. Each packages the app and runs half of the scenarios (`playwright test --shard`; `fullyParallel` is on in `playwright.desktop.config.ts`, since each scenario launches the app on a data folder of its own). When the installer is wanted, only the second job builds it, since the first half of the scenarios takes longer; both test the unpacked executable.

## Visual check

Beside the browser suite, Checks runs `pnpm test:visual` (`tests/visual/visual.spec.ts`, UX-15) in a job of its own. It seeds the demo workspace on a server whose clock stands still and whose random bytes come from a fixed seed (`tests/visual/frozen-server.mjs`), so ids, avatar colours and times are the same every run, and fixes the browser's clock and time zone. Then it walks eight screens on a 1280 by 820 window and four on a 390 by 844 phone, in Onyx and in White, and compares each with its picture in `tests/visual/__screenshots__/linux/` (up to 0.2% of pixels may differ). axe, colour contrast included, must find nothing on each screen.

Fonts are drawn a little differently on each system, so only Linux compares. On Windows and macOS the same screens are walked and checked with axe. `OWNBASE_VISUAL_SNAPSHOTS=1` compares against pictures in a folder for that system, which git ignores, to see whether a change moves anything before CI does.

A change to how the screens look fails the check until the pictures are taken again. Add the `visual baselines` label to the pull request, or run "Visual baselines" from the Actions tab on the branch. It takes, on Linux, only the pictures that no longer match, commits them to the branch, and gets Checks run on that commit: GitHub holds the runs a workflow's own push starts until they are approved, so it approves them, and where there are none to approve it starts Checks by hand. Look at the pictures in the pull request's diff before merging. A failed comparison uploads the expected, actual and difference pictures with the browser results, kept for a day and deleted by the next Checks run.
